# site-scanner

Бот для поиска потенциальных клиентов веб-студии. Идёт по **выдаче Яндекса
и Google** для заданных категорий/городов, сканирует найденные сайты,
оценивает «устаревание» дизайна по набору эвристик, вытаскивает контакты,
**обогащает по ИНН** (оборот, статус, руководитель) и выгружает
**ранжированный список лидов** (CSV + JSON).

Логика простая: у кого сайт древний и кривой, а у компании есть оборот —
тот первый кандидат на редизайн. Чем выше `outdated_score`, тем «горячее» лид.

## Как это работает

```
запросы (категория × город)
   └─ Яндекс + Google (официальные API, с кэшем и ретраями)
        └─ убираем агрегаторы, дубли и уже просмотренные домены
             └─ качаем сайт (детект кодировки, robots.txt, пауза на домен)
                  └─ считаем outdated_score по эвристикам
                       └─ вытаскиваем контакты (+ доходим до /контакты)
                            └─ обогащаем по ИНН (DaData: статус/директор, ГИР БО: оборот)
                                 └─ сортируем ─▶ leads.csv / leads.json
```

## Веб-интерфейс (без командной строки)

Чтобы не возиться с флагами и `export`, есть браузерный интерфейс: форма
настроек, панель API-ключей (вводятся один раз и сохраняются), запуск скана
кнопкой, живой прогресс и таблица лидов с сортировкой и выгрузкой в CSV/JSON.

```bash
pip install -r requirements.txt -r requirements-web.txt
./run_web.sh                      # → http://127.0.0.1:8600
```

Ключи вводятся в панели «API-ключи» и сохраняются в `secrets.local.json`
(в `.gitignore`) — при следующем запуске подхватываются автоматически.
Результаты каждого прогона лежат в `webapp_data/jobs/<id>/`.

В интерфейсе: категории выбираются кликом по чипам (сгруппированный
каталог ниш) плюс можно дописать свои; сверху над таблицей — панель
аналитики со сводкой, а сами лиды ранжируются по приоритету аутрича
(см. ниже).

## Сигнал «живой бизнес» (вкладывается в клиентов)

Во время скана детектятся маркетинговые инструменты на сайте
(`scanner/activity.py`): Яндекс.Метрика, Google Analytics/Ads, чаты (Jivo,
Talk-Me), виджеты обратного звонка, квизы. Их наличие = бизнес **тратит
деньги на привлечение клиентов**, значит охотнее купит и новый сайт. Такой
лид получает +баллы к приоритету аутрича (сильнее, чем «просто старый»
сайт, который могли забросить). В таблице — бейдж «💰 реклама», в сводке —
плитка «вкладываются в рекламу».

## Аналитика: кому писать в первую очередь

Кроме «старости» сайта бот считает **`outreach_score` (0..100)** и
приоритет **A / B / C** — насколько выгодно писать компании предложение о
новом сайте на рабочую почту. В расчёт идут:

- **достижимость по почте** — есть ли email, и особенно **корпоративная
  почта на своём домене** (`info@ихдомен.ru`, а не `firma@mail.ru`);
- **потребность** — насколько устарел сайт (`outdated_score`);
- **бюджет и «живость»** — оборот, статус «действующая», число сотрудников
  (из обогащения по ИНН, если включено).

Таблица по умолчанию отсортирована по `outreach_score`, а плитка «готовы к
письму на рабочую почту» показывает, скольким можно писать прямо сейчас
(корпоративная почта + приоритет A/B). Всё это едет и в CSV
(колонки `priority`, `outreach_score`, `corp_email`).

## Аутрич прямо из интерфейса

- **Кнопка «✉ Письмо»** у каждого лида открывает готовое письмо-предложение:
  тема и текст уже персонализированы — упомянуты конкретные проблемы сайта
  («не адаптирован под смартфоны», «просрочен сертификат», «дизайн устарел»).
  Текст можно поправить и нажать **«Открыть в почте»** (`mailto:` с
  подставленным адресом, темой и телом) или **«Копировать»**.
- **Статусы лидов** (мини-CRM): по каждому — `написал / ответили / клиент /
  отказ` + заметка. Хранятся в SQLite (`webapp_data/leads.sqlite`),
  переживают перезапуски и новые сканы; обработанные подсвечиваются, и их
  можно скрыть фильтром.
- **Фильтры и поиск** в таблице: по приоритету A/B/C, «только с почтой»,
  «скрыть обработанные», поиск по домену/компании.
- **Вкладка «База просканированных»**: каждый скан складывает лиды в
  постоянную БД (`webapp_data/leads.sqlite`, дедуп по домену). В базе видно
  всё накопленное за все прогоны — со статусами, фильтрами и письмом, —
  чтобы результаты не терялись и один и тот же бизнес не обрабатывался
  дважды. Эндпоинт `GET /api/base`.

## Рассылка писем (SMTP)

Письма шлём **с собственного ящика** пользователя (панель «Рассылка (SMTP)»).
Осознанно не «залпом»: холодная рассылка большими пачками = бан ящика и
спам-листы. Отправка идёт **по одному, с паузой (~45 с) и дневным лимитом**
(`webapp/mailer.py`: `DEFAULT_DELAY`, `DEFAULT_DAILY_CAP`), каждому — его
персональное письмо.

- **Настройка**: хост/порт/логин/пароль-приложения + имя отправителя,
  кнопка «Тест себе». Для Яндекс.Почты — `smtp.yandex.ru:465` и **пароль
  приложения** (Яндекс ID → Безопасность → Пароли приложений), не обычный.
- **Одно письмо**: в окне письма кнопка «Отправить с сервера» → шлёт и
  помечает лид «написал».
- **Массовая рассылка**: кнопка «Разослать» шлёт по текущей выборке
  (фильтры) всем, у кого есть почта и нет статуса; в фоне, с прогрессом.
- Эндпоинты: `GET /api/smtp`, `POST /api/send/test`, `POST /api/send`,
  `POST /api/send/bulk`, `GET /api/send/{id}`.

> Юридически холодная B2B-рассылка в РФ — серая зона (закон «О рекламе»
> требует согласия). Малые объёмы с личного ящика — обычный сейлз-аутрич,
> но риск на пользователе.

## Скриншот старого сайта

В окне письма и звонка показывается **превью главной страницы** лида —
визуальный аргумент («вот как ваш сайт выглядит сейчас»). Снимается лениво
по запросу через headless Chromium (`webapp/screenshot.py`) и кэшируется в
`webapp_data/shots/`. Эндпоинт `GET /api/screenshot/{domain}`.

> Для скриншотов в образ ставится Chromium (`playwright install --with-deps
> chromium` в Dockerfile) — образ заметно тяжелее и дольше собирается.

## Воронка (канбан)

Вкладка «Воронка»: лиды по стадиям (Новый → Написал → Звонок → Интерес →
Клиент → Отказ), у каждого — статус и **сумма сделки**. Сверху
«Заработано» = сумма сделок по клиентам, считается автоматически. Поле
`deal_amount` в `lead_state`.

## Обзвон лидов

- **Скрипт звонка** (кнопка «📞» у лида): готовая речёвка под конкретный
  сайт — приветствие, зацепка по его проблеме, оффер, выход на ЛПР и ответы
  на частые возражения. Имя звонящего берётся из настроек рассылки.
- **Клик-звонок**: телефоны в таблице и в окне звонка — `tel:`-ссылки
  (работают с телефона и софтфонов).
- **Воронка обзвона**: статусы `звонил / недозвон / перезвонить / интерес`
  (быстрые кнопки в окне звонка), дата **«перезвонить»** и фильтр
  **«перезвонить сегодня»** — чтобы не терять тех, кому обещал набрать.

## Быстрый старт (командная строка)

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

# ключи поисковиков (см. раздел «Поисковые провайдеры»)
export YANDEX_XML_USER=... YANDEX_XML_KEY=...
export GOOGLE_API_KEY=...  GOOGLE_CSE_CX=...

python -m scanner --category "стоматология" --city "Казань" --min-score 30 --top 15
```

Результат — `leads.csv` (UTF-8 BOM, открывается в Excel/Sheets) и `leads.json`,
отсортированные по `outdated_score`.

Проще всего задать всё в конфиге:

```bash
cp config.example.yaml config.yaml   # отредактировать под себя
python -m scanner --config config.yaml
```

## Что делает бота устойчивым на рунете

- **Детект кодировки.** Старые сайты часто отдают `windows-1251` без
  корректного HTTP-заголовка. Бот определяет кодировку по заголовку →
  `<meta charset>` → авто-детекту, иначе текст читался бы как кракозябры и
  контакты бы терялись.
- **Битый SSL — это сигнал, а не ошибка.** У заброшенных сайтов сертификаты
  просрочены/самоподписаны. Бот не падает: пробует `http`, фиксирует факт
  (`tls_error`) и добавляет баллы к устареванию.
- **Доходит до страницы контактов.** Телефоны и ИНН часто только на
  `/контакты` — бот переходит туда и дополняет контакты (в рамках одного домена).
- **Вежливость.** Уважает `robots.txt` и держит паузу между запросами к
  одному домену (`per_host_delay`).
- **Валидация ИНН/ОГРН по контрольной сумме** — чтобы не тащить случайные
  числа со страницы.
- **Скан не может зависнуть.** У прогона общий дедлайн, у каждой фазы — свой
  бюджет (см. ниже). По истечении фаза отдаёт то, что успела, пишет
  предупреждение в интерфейс и передаёт эстафету дальше.

## Почему скан всегда завершается

Внешние зависимости — поисковик, реестры, сами сайты — могут не ответить
никогда. Таймаута `requests` для этого мало: он считается на одну операцию
с сокетом, а не на запрос целиком, поэтому цепочка редиректов, «струйка»
байт по чуть-чуть или повторы его обходят. Поэтому потолки стоят на фазах:

| Настройка | По умолчанию | Что ограничивает |
|---|---|---|
| `total_budget` | 1800 с | весь прогон целиком |
| `collect_budget` | 240 с | сбор выдачи из поисковиков |
| `scan_budget` | авто (≤600 с) | обход сайтов |
| `enrich_budget` | 600 с | запросы в DaData/DataNewton |

Фаза берёт не больше своего бюджета **и** не больше остатка от общего, а
сканирование резервирует время для обогащения — иначе оно съело бы весь
дедлайн. Дедлайн уходит и внутрь провайдеров поиска: поток, брошенный по
бюджету, перестаёт опрашивать API, а не жжёт квоту ещё полчаса.

Отдельно: список публичных суффиксов для разбора домена берётся из снапшота
в пакете. По умолчанию `tldextract` тянет его из сети при первом вызове и
**без таймаута** — в закрытой сети это подвешивало скан навсегда, причём в
главном потоке, где его не прикрывал ни один бюджет.

## Эвристики устаревания (`scanner/heuristics.py`)

| Сигнал | Баллы |
|---|---|
| Нет `<meta viewport>` (не адаптивный) | +22 |
| Битый SSL-сертификат | +18 |
| Нет HTTPS | +15 |
| Устаревшие теги (`font`, `center`, `marquee`, `frameset`…) | +15 |
| Flash-контент (`.swf`, `<embed>`) | +15 |
| Табличная вёрстка (≥3 таблиц с `width`) | +12 |
| Устаревшая CMS (Joomla 1.x, WordPress 1-3, uCoz, FrontPage…) | +10 |
| Копирайт в футере устарел (© на 3+ года назад) | до +12 |
| Нет DOCTYPE / старый DOCTYPE (HTML4/XHTML) | +7 |
| Старый серверный софт (PHP 4/5, Apache 2.2, IIS 5-7) | до +6 |
| Старый jQuery (< 1.9) | +6 |
| Нет Open Graph / нет `@media` / нет favicon | +5 / +5 / +3 |

Итог обрезается до 100. Все сработавшие сигналы попадают в колонку `signals`.

## Обогащение по ИНН (ГИР БО + DaData)

Тот самый шаг «смотришь оборот». По ИНН со страницы (а если его нет —
резолвим по названию через DaData) бот достаёт официальное название, статус
(действующая/ликвидирована), ФИО руководителя, оборот — и это едет в CSV.

Источники разделены, потому что **бесплатный DaData оборот НЕ отдаёт**:

- **ГИР БО** (https://bo.nalog.gov.ru) — **оборот**. Государственный ресурс
  бухотчётности ФНС: ключ не нужен, лимитов нет, и это первоисточник, из
  которого агрегаторы данные и перепродают. Работает «из коробки».
- **DaData** (`DADATA_TOKEN`, https://dadata.ru/api/find-party/) — название,
  статус, ФИО директора, адрес. Всё это есть и на бесплатном тарифе.
- **DataNewton** (`DATANEWTON_TOKEN`, https://datanewton.ru) — запасной
  источник оборота. Нужен только если у вас платный тариф: на бесплатном
  финансы закрыты, API отвечает `200` с `{"available_count": 0}` вместо отчёта.

```bash
export DADATA_TOKEN=...        # название/директор (оборот работает и без него)
python -m scanner --config config.yaml --enrich
```

Как устроен путь к обороту в ГИР БО (`scanner/girbo.py`): поиск по ИНН →
`id` организации → список сданных отчётов по годам. Поле `gainSum` в этом
списке — это строка **2110 «Выручка»**; сверено с детализацией отчёта, где
`financialResult.current2110` даёт то же число, поэтому в детализацию не
ходим. Суммы в отчётности указаны в тысячах рублей и приводятся к рублям.

Чего в ГИР БО нет: банков (у кредитных организаций своя отчётность), ИП (они
бухотчётность не сдают) и новых ООО до первой сданной отчётности. В таких
случаях в колонке `revenue_note` пишется причина, а не пустота.

В веб-интерфейсе ключи вводятся в панели «API-ключи». Так в топе оказываются
не просто старые сайты, а старые сайты у компаний с деньгами.

## Поисковые провайдеры

По умолчанию бот опрашивает **Яндекс и Google** и объединяет выдачу
(round-robin, дубли доменов убираются). Прямой скрапинг не используется —
оба движка быстро отдают капчу; только официальные API.

**Google — Custom Search JSON API**
1. Ключ: <https://developers.google.com/custom-search/v1/overview>
2. Создать Programmable Search Engine, включить «Search the entire web» → получить `cx`.
```bash
export GOOGLE_API_KEY=...  GOOGLE_CSE_CX=...   # бесплатно 100 запросов/день
```

**Яндекс — Search API**

Провайдер `yandex` сам выбирает формат по заданным ключам:
```bash
# Вариант А — Yandex Cloud Search API v2 (актуальный, нужен платёжный аккаунт):
#   https://yandex.cloud/ru/docs/search-api/
#   ключ сервисного аккаунта + id каталога (folder)
export YANDEX_API_KEY=...  YANDEX_FOLDER_ID=...
# Вариант Б — классический Яндекс.XML (user+key): https://yandex.ru/dev/xml/
export YANDEX_XML_USER=...  YANDEX_XML_KEY=...
```
При наличии `YANDEX_API_KEY`+`YANDEX_FOLDER_ID` используется Cloud v2 (ответ
приходит в base64-XML), иначе — классический XML.

**SerpAPI** — турнкей на оба движка одним ключом:
```bash
export SERPAPI_KEY=...
python -m scanner --provider serpapi_yandex --provider serpapi_google -q "..."
```

Без ключей бот не падает — предупреждает, что задать, и возвращает пустой
список.

## Кэш и инкрементальность

Кэш на SQLite (`cache.sqlite`) экономит квоту поисковиков и позволяет
докручивать список постепенно:

- **выдача поиска** кэшируется (TTL `search_ttl`, по умолчанию сутки);
- **`--skip-seen`** пропускает домены из прошлых прогонов (таблица `seen`);
- **`--cache-pages`** дополнительно кэширует HTML (может разрастись);
- **`--no-cache`** отключает всё.

## Флаги CLI

| Флаг | Назначение |
|---|---|
| `--config FILE` | YAML-конфиг (флаги переопределяют его значения) |

| `--queries-file` | файл со списком запросов |
| `--category` / `--city` | генерируют запросы «категория город» |
| `--provider` | `yandex`, `google`, `serpapi_google`, `serpapi_yandex`, `duckduckgo` (по умолч. yandex+google) |
| `--max-per-query` | результатов на запрос (20) |
| `--concurrency` | параллельных сканов (8) |
| `--min-score` | не включать сайты ниже порога |
| `--timeout` | таймаут запроса к сайту, сек |
| `--total-budget` | потолок времени на весь прогон, сек (1800) |
| `--per-host-delay` | пауза между запросами к одному домену, сек |
| `--no-robots` | не учитывать robots.txt |
| `--no-follow-contacts` | не заходить на страницу контактов |
| `--enrich` | обогатить по ИНН через DaData |
| `--cache-path` / `--no-cache` / `--cache-pages` / `--skip-seen` | управление кэшем |
| `-o, --out` | базовое имя файлов вывода |
| `--top` | вывести топ-N в консоль |
| `-v, --verbose` | подробный лог |

## Структура

```
scanner/
  __main__.py    CLI
  config.py      настройки + загрузка YAML
  search.py      Яндекс / Google / SerpAPI / DuckDuckGo + кэш + ретраи
  fetcher.py     загрузка страниц, детект кодировки, обработка SSL
  politeness.py  robots.txt + пауза на домен
  heuristics.py  оценка устаревания дизайна
  contacts.py    извлечение контактов (+ деобфускация, follow /контакты)
  validators.py  контрольные суммы ИНН/ОГРН
```
