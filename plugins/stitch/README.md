# stitch — экраны интерфейса от Google

Даёт пятнадцать инструментов Stitch прямо в сессии: создать проект,
сгенерировать экран по тексту, отредактировать, наплодить вариантов, собрать
дизайн-систему из `DESIGN.md` и применить её ко всем экранам сразу.

Зачем в студии: это этап **вида** до сборки. Клиенту показываются три разных
первых экрана раньше, чем что-либо собрано в Lovable, а дизайн-система
применяется ко всем экранам одной командой. Промпты пишет Клод — из выгрузки
старого сайта и `DESIGN.md`, по правилам
`.claude/skills/lovable-site/references/napravlenie.md`.

## Ключ

Берётся в кабинете: **stitch.withgoogle.com → иконка профиля → Stitch
Settings → API Keys → Create Key**. Google Cloud, gcloud и биллинг для этого
пути не нужны.

Ключ читается из окружения, в репозитории его нет:

```bash
echo 'export STITCH_API_KEY=...' >> ~/.zshrc   # мак
```

Без переменной сервер поднимется, но каждый вызов вернёт «Request is missing
required authentication credential».

## Почему через мост, а не напрямую

У Stitch есть готовый HTTP-эндпоинт `https://stitch.googleapis.com/mcp`, и
подключить его одной строкой было бы правильно. Не выходит: в схеме
инструмента `upload_design_md` объявлена ссылка `#/$defs/ScreenInstance`, а
само определение сервер не присылает. Клод на неразрешимой ссылке отбрасывает
**весь** список — из-за одного сломанного инструмента недоступны все
пятнадцать. Проверено: при прямом подключении `claude mcp list` пишет
`Connected · tools fetch failed — can't resolve reference #/$defs/ScreenInstance`.

`most.mjs` — тонкая прослойка на Node без зависимостей. Перекладывает JSON-RPC
со stdin в POST и обратно, тащит `Mcp-Session-Id`, и на ответе `tools/list`
дописывает недостающие определения как свободный объект. Смысл схемы не
подменяется — закрывается дыра, чтобы список прошёл проверку целиком.

Две вещи, на которых мост уже спотыкался и которые чинить обратно не надо:

- **выход по закрытию stdin.** При пайпе вход закрывается раньше, чем придут
  ответы. Поэтому выход только когда вход закрыт **и** очередь пуста;
- **запись без подтверждения.** `tools/list` у Stitch весит 324 КБ и не лезет
  в буфер трубы за раз: без ожидания записи ответ обрубался на 64 КБ, и
  клиент получал битый JSON.

## Как вызывать

Инструменты требуют `projectId` **без префикса** `projects/` — с префиксом
приходит «Request contains an invalid argument», и по этому сообщению
причину не угадать. Модель выбирается явно: `GEMINI_3_1_PRO` или
`GEMINI_3_FLASH`.

Генерация одного экрана занимает две-три минуты, и это дольше, чем сессия
готова ждать вызов инструмента. **Потолок ожидания задаётся переменной
окружения `MCP_TOOL_TIMEOUT`, и в облачных сессиях он по умолчанию 60 000 мс.**
С ним `generate_screen_from_text` обрывается на минуте с
«timed out after 60s», экран не создаётся, и `list_screens` остаётся пустым
даже через десять минут — то есть отсечённый вызов не доживает на стороне
Stitch, как можно было бы понадеяться.

Ставить **`MCP_TOOL_TIMEOUT=300000`**, туда же, где лежит `STITCH_API_KEY`: в
переменные окружения площадки. Из сессии её не поменять — клиент читает
переменную при запуске, до всех скриптов. Значит и **вписанная переменная
начинает действовать только со следующей сессии**: в текущей `echo
$MCP_TOOL_TIMEOUT` по-прежнему покажет старое значение, и это не ошибка
площадки. Проверять первым делом в новой сессии. `tools/setup-web.sh` теперь
её проверяет и ругается, если мало.

**Быстрая модель от таймаута не спасает.** `GEMINI_3_FLASH` пробовали вместо
`GEMINI_3_1_PRO` в надежде уложиться в минуту — тот же обрыв на 60 секундах и
тот же пустой `list_screens` через две минуты. Модель выбирается по нужному
качеству, а не ради обхода потолка ожидания.

Что при этом всё-таки происходит за первую минуту: **дизайн-система из промпта
успевает примениться к проекту**. На `textileopt.ru` так и вышло — тема
«Industrial Textile Framework» со всеми величинами из `DESIGN.md` в проекте
появилась, а экрана нет. Так что пустой `list_screens` при живой теме — это
именно таймаут, а не отказ Stitch.

## Чего эта связка не делает

**HTML и картинку экрана Stitch отдаёт ссылками на хосты Google.** Из облачной
сессии они закрыты нашим же прокси (403 на CONNECT), поэтому забрать готовый
код там нельзя: генерация проходит, скачивание — нет. С машины владельца, где
кабинет Stitch открывается, скачивается обычным запросом.

Закрыт не один хост, а оба, которые встречаются: `contribution.usercontent.google.com`
(HTML и картинка экрана) и `lh3.googleusercontent.com` (превью проекта из
`get_project`). Проверено обоими.

Значит порядок работы такой: генерировать можно откуда угодно, **забирать
код — с мака**, и уже оттуда переносить в проект клиента.

## Без ключа сервер не поднимется, но скажет почему

Google отвечает на рукопожатие без ключа **HTML-страницей 401**, а не JSON.
Раньше мост её не разбирал и молчал — сессия ждала свой таймаут и объявляла
сервер мёртвым «connection timed out after 30000ms», хотя дело было только в
переменной. Теперь на любой неудачный ответ мост возвращаетJSON-RPC ошибку с
человеческой формулировкой, и причина видна сразу.

## Проверено вживую

- ключ из кабинета работает: `list_projects` отвечает без ошибки;
- через мост поднимаются все 15 инструментов, `ScreenInstance` определён;
- `create_project` + `generate_screen_from_text` (Gemini 3.1 Pro, DESKTOP)
  создали экран за ~2 минуты;
- в аккаунте владельца остался тестовый проект **«Проба механизма — Проект
  Дома»** — можно удалить, `delete_project`;
- без ключа мост отвечает ошибкой за секунду, а не висит 30 секунд.
