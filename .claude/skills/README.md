# Скилы: инструкции для Клода под работу над сайтами клиентов

Скил — это папка с `SKILL.md`, которую Клод подхватывает сам, когда задача
похожа на описанную во фронт-маттере. От CLAUDE.md отличается тем, что тело
скила грузится только в момент применения: длинную методичку можно держать
рядом с проектом, и она ничего не стоит, пока не понадобилась.

Включать ничего не надо. Скилы из `.claude/skills/` подхватываются
автоматически — и в терминале, и в веб-сессиях Claude Code, потому что там
репозиторий клонируется целиком. Позвать явно — `/имя-скила`.

Где эти папки **не** работают: чат на claude.ai и Cowork читают скилы,
включённые в аккаунте, а не в репозитории.

## Свой: весь цикл сайта клиента

**`/lovable-site`** — этапы 4–7 из `clients/СХЕМА.md`, собранные в процедуру:
разбор выгрузки старого сайта, промпты для Lovable по блокам, правка проекта
кодом вместо промпта, вычистка следов конструктора, выкладка на VPS, проверка
перед показом. Плюс красные линии, каждая из которых уже стоила денег или
времени: не трогать MX при переносе домена, не выдумывать услуги в промптах,
не править `vite.config.ts`, не сливать ветку `deploy` в `main`.

Следы Lovable проверяются скриптом, а не памятью:

```bash
.claude/skills/lovable-site/scripts/check-lovable.sh /root/prototypes-static/<имя>
```

Ищет `cdn.gpteng.co`, бейдж «Edit with Lovable», `<title>` вида «Lovable
Generated Project», `<meta name="generator">` и og:image на чужом домене.
Выход 1 — выкладывать нельзя. Пересборка возвращает следы обратно, поэтому
проверка идёт перед каждой выкладкой.

Вторым скриптом проверяется, не видно ли, что страницу собрала нейросеть:

```bash
.claude/skills/lovable-site/scripts/check-shablon.sh <папка сайта>
```

Уровень «стоп» — чужие фото со стока, чужой телефон, рыба, английские кнопки,
выдуманное «Trusted by 10 000+»: выход 1, показывать нельзя. Уровень «шаблон» —
градиентный текст, фиолетово-розовый градиент, эмодзи вместо иконок,
надзаголовок над каждой секцией, всё подряд в карточках: показывается, но
решает человек.

Внутри `references/` — разбор дампа (шесть пунктов на выходе и грабли),
правила промптов (порядок блоков, что запрещено выдумывать) и `palevo.md`:
что ловится скриптом, что только глазами и какие запреты вписать в первый
промпт, чтобы не переделывать за кредиты.

## Три заимствованных, которые нужны каждый раз

Порядок работы над прототипом: сначала придумать вид, потом собрать, потом
проверить, что это можно сдать.

**`/frontend-design`** — как придумать вид. Заставляет сначала выписать план
(палитра из 4–6 названных цветов, пара шрифтов, схема раскладки, один
фирменный элемент), проверить его на шаблонность и только потом писать код.
Отдельно перечислены три вида, к которым скатывается любая нейросеть
(кремовый фон + сериф + терракота; чёрный фон + кислотный акцент; «газетная»
вёрстка с волосяными линейками) — их брать запрещено, если бриф не просит.

**`/web-design-engineer`** — как это сделать руками. Три части, ради которых
он и взят:

- `references/style-recipes/` — 25 названных видов с готовыми палитрами,
  шрифтами, радиусами и шагом сетки: Stripe Press, Linear, Raycast, Aesop,
  Muji, Braun Дитера Рамса, Apple HIG, Tufte и другие. Годится как меню для
  разговора с клиентом: не «сделаем красиво», а «вот три направления».
- `references/redesign-protocol.md` — протокол переделки существующего сайта:
  сначала классифицировать работу (доработка / редизайн с сохранением
  айдентики / полная замена), снять аудит текущего состояния, выписать, что
  трогать нельзя. Это ровно наша работа, и обычно её делают на глаз.
- `references/failure-patterns.md` — каталог признаков «это рисовала
  нейросеть», каждый в виде «дефолт → почему плохо → как обнаружить → чем
  заменить». Повторяющиеся мелкие надзаголовки над каждой секцией, три
  подряд блока «картинка слева / текст справа» и прочее, что видно в любом
  первом выводе Lovable.

**`/web-quality-audit`** — можно ли это сдавать. Проверка по 150+ пунктам
Lighthouse, тянет за собой соседей `/seo`, `/accessibility`,
`/core-web-vitals`, `/performance`, `/best-practices` (они же вызываются
отдельно). Lovable стабильно отдаёт страницу без description, без Open Graph,
без alt у картинок, без sitemap и с картинками в оригинальном разрешении —
клиенту это продаётся как сайт, а находиться в поиске он не будет.

## Остальное

**`/theme-factory`** — десять готовых пар «палитра + шрифты» и PDF-показ.
Быстрый ответ на «покажите варианты», когда style-recipes избыточны.

**`/webapp-testing`** — Playwright: открыть свою страницу, прокликать,
снять скриншоты, посмотреть консоль. Chromium в образе уже стоит (ставился
ради скриншотов в сканере). Нужен, чтобы Клод смотрел на свою работу
глазами, а не сдавал вслепую.

## Что сознательно не взяли

**3D и тяжёлая анимация** (`freshtechbro/claudedesignskills`: three.js, GSAP
ScrollTrigger, Lottie, Spline, R3F). Соблазнительно, но клиентов смотрят с
телефона на мобильном интернете, а три библиотеки анимации убивают Core Web
Vitals — и ту самую выдачу, ради которой сайт заказывают. Если под конкретный
проект понадобится скролл-эффект, скил ставится точечно, а не пачкой.

**`bzsasson/pre-launch-audit-skill`** — хороший предзапусковый чек-лист, но
перекрывается с `web-quality-audit` и рассчитан на Screaming Frog и
DataForSEO, которых у нас нет.

**`xiaopu-ai/web-design`** — тот же подход «сначала спецификация, потом код»,
но `SKILL.md` на китайском: читать и править нам его тяжело.

**`jiji262/claude-design-skill`** — про артефакты claude.ai, у Клода для
этого есть встроенный `artifact-design`.

**`brand-guidelines`** из `anthropics/skills` — фирстиль самой Anthropic.

Копии не изменены, `LICENSE.txt` внутри каждой папки — часть условий, удалять
нельзя. Начнём править под себя — обе лицензии требуют пометить в `SKILL.md`,
что именно поменяли.

Обновить или добавить ещё один скил:

```bash
git clone --depth 1 https://github.com/addyosmani/web-quality-skills /tmp/wq
cp -r /tmp/wq/skills/<имя> .claude/skills/ && cp /tmp/wq/LICENSE .claude/skills/<имя>/LICENSE.txt
```

Скрипт `web-quality-audit/scripts/analyze.sh` требует `jq`; без него скил
работает, но разбор HTML придётся делать чтением файлов.

## Почему копиями, а не плагинами

Второй способ — прописать маркетплейс в `.claude/settings.json`:

```json
{
  "extraKnownMarketplaces": {
    "anthropic-agent-skills": {
      "source": { "source": "github", "repo": "anthropics/skills" }
    }
  },
  "enabledPlugins": { "example-skills@anthropic-agent-skills": true }
}
```

Так скилы сами обновляются, но ставятся пачкой целиком (у Anthropic — все
двенадцать, включая постеры на 5,6 МБ и генератор гифок для Слака), тянутся из
сети в начале каждой сессии и требуют доверия к папке. Копия в репозитории
предсказуемее и работает без сети.

## Как добавить свой скил

`.claude/skills/<имя>/SKILL.md` с фронт-маттером `name` и `description` —
имя папки становится командой `/<имя>`. Смысл заводить скил появляется там,
где процедура повторяется и её каждый раз перечитывают целиком: `lovable-site`
вырос ровно из этого. Описание в `description` должно называть, **когда** его
применять, — по нему Клод решает, подтягивать скил или нет.

Файлы в `references/` грузятся только когда до них дошло дело, поэтому длинные
куски лучше держать там, а в `SKILL.md` оставлять порядок действий.
