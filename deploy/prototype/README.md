# Прототипы клиентов на своём сервере

Прототип, собранный в Lovable, живёт по адресу вида `…lovable.app`. Показывать
клиенту такую ссылку можно, но свой домен выглядит солиднее, не зависит от
чужого сервиса и не пропадёт, когда проект в Lovable переделают под
следующего клиента.

## На сервере ничего не собирается

**Проверено на живом, дважды.** VPS этого тарифа — 961 МБ памяти и одно ядро;
`bun run build` там получает SIGKILL от OOM-killer после ~13 минут свопинга.
Второй сервер, взятый чистым, оказался того же размера, и результат тот же.
Своп не спасает: сборка уходит на диск и всё равно вылетает.

Поэтому **проект собирается вне сервера, а на сервер уезжает результат** —
в ветку `deploy` того же репозитория: готовая разметка `index.html`,
клиентский бандл и фотографии, около 3 МБ.

Рантайма тоже нет. Страница статическая, отдаёт её Caddy: ни node, ни
контейнера на клиента, ни перезагрузки при обновлении. Сервер под это
годится любой, даже эти 961 МБ — работы ему секунды.

Ветка `deploy` **генерируется** и перезаписывается принудительным пушем.
Руками её не правят и в `main` не сливают: `main` синхронизирован с Lovable.

## Развернуть сервер прототипов

Разово, на чистой машине (Debian 12 или Ubuntu 24.04):

```bash
curl -fsSL https://get.docker.com | sh
git clone https://github.com/Rklm-it/site-scanner.git /root/site-scanner
cd /root/site-scanner/deploy/prototype
docker compose up -d
```

Поднимется Caddy стека `prototypes`. Он отдаёт файлы из
`/root/prototypes-static/<имя>` — папку принесёт `sync.sh`.

## Выложить прототип клиента

Домен: заведите поддомен и направьте A-записью на IP **этого** сервера.
Один поддомен на клиента — не перепутаете, и погасить можно по отдельности.

```bash
cd /root/site-scanner/deploy/prototype
./sync.sh projekt-doma https://github.com/Rklm-it/project-house-design.git
```

Секунды. Перечитывать Caddy не нужно: файлы читаются на каждый запрос.

## Прототип, собранный кодом (без Lovable и без репозитория)

У «Папиной лавки» макет — одна страница, которую собирает скрипт из выгрузки.
Репозитория у неё нет, поэтому `sync.sh` не нужен: файлы кладутся прямо в
`/root/prototypes-static/<клиент>`.

```bash
cd /root/site-scanner
git checkout main && git pull origin main
python3 clients/papinalavka.ru/макет/собрать.py \
        /root/prototypes-static/papinalavka/index.html --файлами
```

`--файлами` кладёт картинки отдельной папкой `img/` рядом: страница выходит
0,4 МБ вместо 3 МБ, браузер кэширует картинки и при следующем заходе тянет
только разметку. Без ключа всё вшивается в один файл — это для отправки
клиенту вложением, не для сервера.

**Обновление после правок — та же команда, и всё.** Caddy трогать не нужно:
файлы читаются на каждый запрос. Пересоздавать контейнер надо только когда в
`Caddyfile` появился новый домен.

**Сервер должен стоять на `main`.** Один раз он уже оказался на ветке клиента
(`claude/dreamy-turing-jfri6b`), и `git pull` вставал с «divergent branches», а
свежие файлы не приезжали — выглядело как поломка выкладки. Проверить, где вы:
`git branch --show-current`.

**Обновить после правок в Lovable — та же команда**, но сначала кто-то должен
пересобрать ветку `deploy`. Пока это делаю я в сессии: правки всё равно
проходят через меня. Чтобы ветка обновлялась сама, нужен GitHub Actions —
это открытая задача.

**Доступ нужен только к приватному репозиторию.** У публичного (например
`Rklm-it/textile-city-essentials`) `sync.sh` клонирует ветку `deploy` без
всяких ключей — ни токена, ни ssh-ключа на сервере заводить не надо. Если же
репозиторий прототипа приватный, один раз выполните
`git config --global credential.helper store` и введите логин и токен GitHub
с правом **Contents: Read** при первом `sync.sh` — дальше запомнится.

Отличить, не заходя на GitHub: приватный отвечает на `git ls-remote <url>`
запросом логина или `Repository not found`, публичный сразу печатает ссылки.

## Перед выкладкой: вычистить следы Lovable

**Обязательно и каждый раз.** Клиент смотрит на сайт своей компании, и бейдж
чужого конструктора в углу превращает показ работы в показ инструмента. К тому
же по этому бейджу заказчик за минуту выясняет, что «сайт собран мышкой», —
разговор о цене после этого другой.

Что искать в собранной ветке:

```bash
grep -rniE 'lovable|gpteng|gptengineer' /root/prototypes-static/<имя> \
  --include='*.html' --include='*.js' --include='*.json' | head -20
```

Убрать нужно:

- скрипт `https://cdn.gpteng.co/gptengineer.js` из `index.html`;
- бейдж «Edit with Lovable» — блок в правом нижнем углу страницы;
- `og:image` и `twitter:image`, ведущие на домены Lovable, — вместо них
  скриншот самого сайта клиента;
- favicon по умолчанию и `<title>` вида «Lovable Generated Project»;
- `<meta name="generator">` с упоминанием конструктора.

Пересборка возвращает всё это обратно, поэтому проверка идёт перед **каждой**
выкладкой, а не один раз при заведении клиента.

## `try_files` глотает картинки, и это видно только через неделю

**Грабля, стоившая круга.** В блоке стояло

```
file_server
try_files {path} {path}/ /index.html
@foto path /images/*
header @foto Cache-Control "public, max-age=604800"
```

Одностраничнику нужен запасной путь на `index.html`, но `try_files` не
разбирает, что именно не нашлось: `/images/rabota-01.jpg` при отсутствующем
файле тоже получал **`index.html` с кодом 200**, а правило ниже штамповало на
этот ответ «кэшировать неделю».

Дальше беда становится незаметной. Пока фотографий в сборке нет, браузер
складывает разметку под адреса всех картинок и **неделю отдаёт её из кэша, не
спрашивая сервер**. Выкладываешь фотографии — на странице по-прежнему пусто, и
выглядит это как несработавшая выкладка: `sync.sh` отчитался, файлы на диске
лежат, `curl` отдаёт картинку, а в браузере ни одной. Так и случилось с
мебельщиком.

Правильная схема — файлы отдавать файлами, одностраничником только остальное:

```
@fayly path /assets/* /images/* /favicon.ico /og.png /robots.txt
handle @fayly {
	file_server
}

handle {
	try_files {path} {path}/ /index.html
	file_server
}
```

И `file` в матчере кэша, иначе долгая метка вешается и на 404:

```
@foto {
	path /images/*
	file
}
header @foto Cache-Control "public, max-age=604800"
```

Проверено настоящим Caddy: существующая картинка — `200 image/jpeg`,
отсутствующая — `404` без заголовка кэша, ссылка с «хвостом» по-прежнему
приводит на `index.html`.

**Как это чинится у того, кому уже показывали ссылку.** Кэш у него в
браузере, и новая выкладка его не трогает. Жёсткое обновление — Ctrl+Shift+R
(на маке ⌘+Shift+R). Клиенту такого не объяснить, поэтому чинить надо **до**
отправки ссылки.

## Блок в Caddyfile

Блоки лежат в `deploy/prototype/Caddyfile` **в репозитории**, там же готовый
образец для `projekt-review.nexus-flow.ru`. Скопируйте, поменяйте домен и имя
контейнера, закоммитьте.

Руками на сервере не правьте: файл под git, и ручная правка делает рабочее
дерево «грязным». После этого `git pull --rebase` отказывается работать до
`stash` или `checkout` — на этом уже дважды застревали при обновлении сканера,
каждый раз посреди дела.

Применить после `git pull`:

```bash
cd /root/site-scanner/deploy/prototype
docker compose up -d --force-recreate caddy
docker compose exec caddy grep -c <домен> /etc/caddy/Caddyfile   # проверка: 1
```

**Почему пересоздание, а не `reload`.** В контейнер примонтирован один файл
(`./Caddyfile:/etc/caddy/Caddyfile`), а `git pull` не правит файл на месте: он
пишет новый и переименовывает. Inode меняется, bind-mount продолжает
указывать на старый — контейнер видит **прежний** конфиг. `reload` при этом
честно отвечает `config is unchanged` и выглядит как успех, а домена в
конфиге нет: браузер получает `tlsv1 alert internal error`, потому что Caddy
не знает имени и сертификат не запрашивает. На rgz61 это стоило получаса.

`restart` не помогает — нужен именно `--force-recreate`. Простой пара секунд,
остальные прототипы переживают.

Если правите Caddyfile прямо на сервере (файл меняется на месте, inode тот
же), достаточно обычной пары:

```bash
docker compose exec caddy caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
docker compose exec caddy caddy reload --config /etc/caddy/Caddyfile --adapter caddyfile
```

Сначала `validate`: если Caddy не примет конфиг, `reload` не тронет рабочий.

## Почему так, а не иначе

**Почему не статикой.** Nitro умеет пресет `static`, но сборка Lovable с ним
падает: `rolldownOptions.input should not be an html file when building for
SSR`. Пресет `node-server` работает, и заодно страница приезжает готовой
разметкой — 30 КБ со всем текстом, а не пустой оболочкой. Для сайта, который
потом будут индексировать, это правильнее.

**Почему переменная окружения, а не правка конфига.** Lovable собирает проект
под Cloudflare, и `node .output/server/index.mjs` на таком выводе падает с
`ERR_MODULE_NOT_FOUND`. Чинится переключением пресета — но если поменять
`vite.config.ts`, изменение уедет обратно в Lovable и сломает превью.
`NITRO_PRESET` задаётся только при сборке образа и в репозиторий не попадает.

**Почему статика, если сборка всё равно SSR.** Пресет `static` у nitro на
сборке Lovable падает, но готовую разметку можно снять с запущенного
node-сервера обычным запросом и положить рядом с бандлом. Проверено
браузером: фильтр каталога отсекает 12 карточек до 2, модалка открывается,
ошибок в консоли нет. То есть интерактив живёт на клиенте и сервер ему не
нужен.

**Dockerfile и deploy.sh оставлены** — они рабочие и понадобятся, если
появится машина, где сборка проходит. Тогда `deploy.sh` вместо `sync.sh`
и `reverse_proxy` вместо `file_server`.

## Снять прототип

Когда сделка закрыта или клиент отказался:

```bash
rm -rf /root/prototypes-static/projekt-doma
```

И убрать блок из `deploy/prototype/Caddyfile` с последующим `reload`.
